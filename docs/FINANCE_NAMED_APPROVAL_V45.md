# Work OS · 财务具名账号与独立审批（Schema 45）

## 本次代码

- 只有显式设置 `WORKOS_AUTH_MODE=named` 才启用具名账号；默认保留现有**本地单人模式**，不会悄悄接管已有用户。
- 具名角色：`owner`、`finance_clerk`、`finance_approver`、`viewer`。后端验证权限，不能只靠前端隐藏按钮。
- 密码只存 scrypt 哈希；同一设备下以 HttpOnly、SameSite=Strict 的短期会话识别操作人。用户停用后，旧会话下一次请求自动失效。
- 财务录入员可以创建个人垫付待审单；只有有审批权限的**其他具名账户**才能使该单过账。提交、审批人及时间均留在 `finance_personal_advance_reviews`。
- **月结独立审批**：提交人完成全部核对并发起待审申请，系统在另一位具名审核员批准时重新计算关账阻断项，随后以同一数据库事务写入 `period_locks` 与 `finance_period_close_requests` 审计记录。申请人不能自己批准，待审申请可以撤回后重新提交；具名模式下旧 `POST /api/periods/close` 直接关账入口拒绝执行。
- **财务高风险操作双人审批**：银行流水核销、手工调整分录及发票税务状态变更在具名模式下先生成 `finance_action_reviews` 申请；由其他具名审批人完成复核。原业务操作和审核审计在同一个数据库事务提交，执行失败整体回滚。对发票税务状态会核对提交时的旧状态，防止过时申请覆盖新认定；银行认领按去除用户伪造动作键的业务内容计算指纹，阻止更换申请编号造成重复核销。
- `approved_by` 等审批人标识从服务端会话派生，不能通过接口自行填写来冒名。无明确提交人身份的旧垫付单在具名模式下**拒绝审批**，需人工补齐来源核验。
- 单据摘要仍按原有 `personal_advances` 规则记账，保障一次审批只过账一次；重复重试不复制费用、应付或银行流水。

## 初始化（仅在本地或 NAS 的受控终端操作）

1. 在**测试账套**完成 Schema 44→45 的迁移；迁移 SQL 位于 `backend/migrations/45_named_finance_users.sql`。
2. 在私有配置中显式设置 `WORKOS_AUTH_MODE=named`。联网 Neon 启动仍需 R2/NAS 原有必要配置。
3. 以命令行交互方式创建至少两名不同人员的账号，输入密码时不回显，也不写入命令参数：

```sh
python backend/manage_finance_users.py add --username account01 --role finance_clerk
python backend/manage_finance_users.py add --username reviewer01 --role finance_approver
```

4. 分别使用两名账号在受控本地页面测试“录入→审批→凭证→不可重复入账”，再核验数据库审计记录和月结。

## 月结实际操作

- 单人本地模式：保留原关账流程。
- 具名模式：经营报表 → 关账检查 → 提交独立审批；财务中心 → 财务审批 → 由另一名有审批权限的具名用户「复核并锁账」。
- 新增 `GET /api/periods/close/requests`、`POST /api/periods/close/request`、`POST /api/periods/close/approve` 与 `POST /api/periods/close/cancel`；不创建自动财务审批人、不预设密码。
- 当系统阻断项存在、审核人为同一账号或账期已结时，后端拒绝锁账；审批成功后重复请求不新增锁账记录。

## 三类高风险操作实际操作

- 具名模式：财务中心原有银行认领、调整凭证、发票税务状态按钮执行「提交审核」，**不会立即入账**；顶部会显示「待他人审批」。
- 另一名 `owner` 或 `finance_approver` 账号在「财务中心 → 财务审批 → 财务高风险操作审批」查看原始申请内容，再点击「审核并入账」。
- 提供 `GET /api/finance/reviews`、`POST /api/finance/reviews/request`、`POST /api/finance/reviews/approve`、`POST /api/finance/reviews/cancel`；具名模式禁止直接调用原三个写入接口绕过审核。
- 同一账号不能提交和批准同一笔请求。批准、取消和重复提交均保留审计信息；审批失败不写财务凭证。

## 安全边界

- 这仍然是**仅绑定本机 loopback 的 API**；未实现面向公网的 HTTPS/反向代理认证、集中持久会话、正式身份提供商接入。不能因此声称已具备生产公网部署条件。
- 已强制角色门禁的高风险接口包括个人垫付审批、银行分配、手工分录、月结、发票税务状态、外币估值与期初余额，以及**税率字典变更、银行对账确认、账户清单完整性确认、费用来源确认、存货调整、平台对账确认、采购收货更正、销售退款/退货、费用分摊冲回**。动态路径使用服务器端路径匹配拦截，不依赖前端隐藏按钮。
- **个人垫付、月结、银行资金分配、手工分录和发票税务状态**已有提交人与审批人分离的强制流程；但账户对账确认、成本修改、期初余额、税率规则变动及其他受限接口仍只有角色门禁，还不是覆盖全部高风险变更的双人审批工单。
- 旧单密码模式不代表正式的具名审批。正式上线必须在配置和备份核验后切换具名模式，防止旧模式绕过角色隔离。
- 未修改正式 Neon 分支，也没有创建默认用户、预置密码或做任何实账过账。
