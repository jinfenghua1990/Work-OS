# ALSVID × Work OS 财务一体化架构（2026-11-21）

## 1. 唯一数据源

| 事项 | 业务权威数据源 | 唯一财务权威数据源 |
| --- | --- | --- |
| ALSVID 采购 PO、工厂交付、到货入库、VIN、库存、销售、退货 | ALSVID Admin 数据库 | 不在 Work OS 重建 |
| 咖啡采购、到货、销售、库存 | Work OS 咖啡业务模块 | Work OS |
| 单场展会项目、费用和预算 | Work OS 展会模块 | Work OS |
| 银行账户、原始银行流水、核销和账务凭证 | — | **Work OS** |
| 进项/销项发票、用途状态、原始文件 | — | **Work OS** |
| 个人垫付、应报销及公司公账报销 | — | **Work OS** |
| 原始凭证（每个上传批次不可变 SHA-256） | 来源归属在引用元数据 | Work OS 原件库 / R2，NAS 镜像 |

两个独立 Neon 数据库，不进行跨库 SQL JOIN，不把数据库密码给对方。由服务端 HTTPS + scoped 身份认证 API 在边界做同步；当前服务端 API 仍限 loopback，生产 ALSVID 对接**尚未实现或验证**。

## 2. Work OS 的 ALSVID 四个页面

1. **经营总览**：展示 Work OS 已识别的 ALSVID 付款、收款、应收应付、发票及个人报销；真正的采购订单数、销售金额、库存、完整利润在 ALSVID API 验证前显示“未接入”，不可用本地旧订单数冒充。
2. **财务对账**：从 Work OS 唯一银行池、发票池与往来核销中筛选归属于 ALSVID 的交易；可以跳往财务中心处理，不能在自行车模块再建采购单。
3. **异常中心**：未连通、逾期往来、发票尚未关联单据、缺银行或发票原件、发票跨业务线混用、个人垫付待审核/待报销、旧业务账与新系统待迁移。全球未认领银行流水不能凭金额猜成 ALSVID。
4. **同步记录**：接口状态、上次已验证同步时间、版本、拒收事件和可追溯差异。接入前显示“尚未连接 / 无同步记录”，不填造假的成功日志。

## 3. 财务做账与业务关联原则

- **ALSVID 创建采购单**：只同步业务承诺与付款计划，不自动入成本或重复记应付。
- **验收的实货入库/结算义务**：ALSVID 发唯一业务事件，在 Work OS 产生一次存货/应付；须先确认公司主体、外币汇率与税额口径。
- **销售履约**：按业务确认收入/应收与对应销售成本/库存结转，付款与开票都不得再次产生第二笔收入或成本。
- **工厂付款**：Work OS 认领银行交易并核销应付；ALSVID 页面读取已付/未付结果；分批可对应同一个 PO。
- **发票**：Work OS 归档、按税号/发票号码去重并关联业务事件；发票本身不代表已付或税局准予抵扣。
- **个人替公司付款**：Work OS 先关联原供应商应付、把债权人转成个人报销应付，*不重复确认采购成本或费用*；公司公账转账给个人后再从银行流水核销个人应付。个人银行卡原交易并非企业银行流水。
- **冲销、更正、退货**：生成反向事件和凭证，不删除历史已过账记录。
- **币种**：原币不可混加，外币账面估值与汇兑需复核；自行车经营分析按 EUR 主展示要求设计，但现有 Work OS CNY 总账仍不能冒充完整 EUR 实际利润报表。

## 4. 对接 API 预留契约（**尚未正式开放**）

| 方向 | 计划用途 | 事件 / 记录身份 |
| --- | --- | --- |
| ALSVID → Work OS | 采购 PO、付款计划、入库、销售履约、退货等不可变业务事件 | `source_system="alsvid"` + `source_document_id` + `event_id` + `revision` |
| Work OS → ALSVID | 应收/应付状态、付款核销、票据原件引用、个人垫付与报销状态 | `finance_id` + `source_document_id` + `booked_at` |
| Work OS 本地只读 | `GET /api/alsvid/finance/overview?period=YYYY-MM`（**已实现**） | 登录后可查，非外网公开接口 |

**计划接收业务事件的基本字段**：`source_system`、`event_id`、`source_document_id`（ALSVID 内部不可变 ID）、`document_no`（供人看）、`event_type`、`revision`、`entity_code`、`currency`、`amount`（十进制字符串）、`effective_on`、`occurred_at`、`payload_checksum`。

正式接入必须先实现：

1. **认证**：独立最小权限 service token、HTTPS、精细角色及 API 审计；绝不能将当前 loopback 管理员 cookie 当服务端集成鉴权。
2. **事件收件箱**：`event_id` 幂等；同一事件不同哈希拒收并记录异常；按业务文档 revision 检查顺序，乱序重试，不能依赖“最新状态覆盖历史”。
3. **业务映射**：同一来源业务文档只能对应一个正式财务承诺/凭证的可追溯引用，迁移旧数据必须先核对、禁止双记。
4. **去重与核销**：银行去重以银行账户+交易唯一标识为准；发票依税号+类型+票号+日期等必要票据身份字段校验；财务核销不依赖人工重复录入。
5. **回传**：财务状态以 Work OS 的版本/发生时间发布给 ALSVID，ALSVID 仅显示，不在其数据库再次独立记一套正式财务账。
6. **环境验收**：Neon 测试分支+测试事件+异常重放+R2 原件校验+真实 NAS 恢复演练；生产切换前两边账务按事件逐笔核平。

## 5. 已实施的防重约束

- Work OS `/bike` 只有只读的四个财务工作区，不再提供重复创建 ALSVID 采购单/收货/销售的操作入口。
- Work OS 的旧 `POST /api/bike/*` 路由回复 HTTP 410；旧 GET 记录保留供历史核对，不删历史、不假定已经迁移。
- `GET /api/alsvid/finance/overview` 返回基于 Work OS 现有财务流水/发票/报销表的**真实归属数据**，不会进行写入、分录或凭证修改。
- 没有经过认证的 ALSVID 业务接口与历史对账，当前默认“未连接”，不会自称已同步或已经取得全量利润。

## 7. 本机双数据库差异预检查（**只读，不迁移**）

为避免把 ALSVID 已存在的人工付款当成真实银行流水，先从本地 Mac/NAS 读取两套 Neon 数据库进行差异检查。该命令对两个数据库都使用 PostgreSQL 的 **REPEATABLE READ + READ ONLY** 事务，不建立表、不写财务凭证、不确认收付款，也不把来源原件换成处理后记录。

在本地私有且不提交的 `.env` 中配置：

```env
WORKOS_DATABASE_URL=postgresql://WorkOS连接地址
ALSVID_DATABASE_URL=postgresql://ALSVID连接地址
```

需在本机安装 `backend/requirements.txt` 的 psycopg 驱动。运行：

```bash
python backend/audit_alsvid_finance.py > alsvid-finance-audit.json
```

检查项目：

- ALSVID 财务义务按 **唯一 ID + 方向 + 原币金额 + 币种** 与 Work OS 显式引用进行对照；无映射、金额冲突、重复关联分别标记，不能仅凭金额猜。
- ALSVID `finance_payments` 只能作为**待核对付款登记**，不是已证明的银行流水：未来日期直接拦截、无原始银行唯一流水号或账户证明的保持待人工复核。匹配要求银行流水号、方向、原币金额、币种和实际日期全部相同且唯一，同一银行流水不可对应两条独立付款证据。
- ALSVID 财务单据不可自动识别为进项或销项税务发票。Work OS 中的 `source_system + source_document_id` 作为票据唯一来源引用，重复 ID 会报警。
- 对两个数据库只查询、输出差异 JSON（最多展示前 100 个异常），不会将 ALSVID 已存在的付款、采购或销售写入 Work OS，也不会改变 ALSVID 的应付状态。
- 数据量超出单表 5,000 行时停止并要求有审核依据的分批范围，不把不完整采样伪装成全量核对。

**预检查结果不是两库已同步的证明。** 真实原件与业务凭据、应收应付确认、正式双向 API、账务切换均未验收前，不进行正式数据迁移或自动过账。
