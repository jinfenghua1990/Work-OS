# 咖啡销售导入防重：本轮落地与限制

## 目标与实现

本次只修改咖啡销售导入，不修改自行车、展会、银行流水或发票核销规则。

- 咖啡业务 CSV 界面要求映射 **渠道、店铺、原始订单号、订单行号**，先预览后确认过账。
- 后端 `POST /api/sales/import-row` 根据这四项和固定业务事件 `sale` 生成统一 SHA-256 来源键，不使用文件名判定业务唯一性。
- 重复来源键且内容未变：返回已处理记录，不生成第二张收入/成本凭证，不重复扣库存。
- 重复来源键但 SKU、日期、数量、单价、渠道、项目等已变：阻断过账，要求人工复核，不静默覆盖。
- 当前导入接口只处理已履约销售：`refund`、`cancel`、`return` 等事件不得伪装成新销售。实物退货仍走原有退货 API。
- 采购验收入库、FIFO 成品/包装盒扣减和原有财务凭证继续复用 Work OS 的同一套账。
- 测试：`python -m unittest discover -s backend/tests -v`；前端：`npm ci && npm run build`。测试只使用临时 SQLite 账套，不连接 Neon。

## 兼容性

旧 API 客户端如果只提供 `source_row_key`，仍使用旧键以免破坏对接；**旧键无法保证跨文件防重**。
存量已过账记录也不会自动按新规则反向匹配或重算。如需迁移历史导入键，必须先只读核对历史销售订单及来源文件，出具差异清单后再执行安全迁移。

新键格式为 `coffee:sale:v2:<SHA-256>`，后端在存量 `import_rows` 与 `sale_lines` 的来源键里使用它。键只识别业务事实，不把哈希当作文件原件的保存证明。

## 未完成（不得声称已交付）

1. **原始凭证归档**：浏览器仍仅解析 CSV，原件不上传服务器。统一文件档案 API、R2/NAS 保存、原件 SHA-256、导入批次和不可变审计尚未交付。用户须在外部安全保存原文件。
2. **Excel**：当前只支持 UTF-8 CSV，原始 `.xlsx` 解析未开发。
3. **来源事件**：取消订单、仅退款、退货入库的统一导入流水还需分别建模；现有退货 API 不代表“仅退款”已实现。
4. **历史对账**：旧 CoffeeBear 和原来的 Work OS CSV 记录尚未完成去重迁移，不能自动认定完全无重。
5. **经营分析**：月平均库存、周转天数、平台扣点等仍需后续独立验收。
6. **正式数据库与权限**：不能将此提交等同于 Neon 生产验收或多系统安全接入。

## 验收口径

独立测试应覆盖：100 件成品成本 10 元、100 个盒成本 2 元、包装 1:1；卖出 10 件、售价 20 元，确认收入 200 元、FIFO 成本 120 元、毛利 80 元；复制/改名文件不得重复入账；同订单变更价格被拒；不同订单相同行号可独立过账；退款事件不得增加销售。
