# Work OS

**多业务经营管理工作台 / Multi-business Operations Workspace**

> 项目状态：**架构基线与实施规范已建立，业务系统尚未开发、部署或验收。**
>
> 目标仓库：`jinfenghua1990/Work-OS`。本仓库是全新项目，不直接复制 CoffeeBear 旧代码、历史 Alembic 迁移链或适配器。

## 一句话定位

**咖啡、自行车、展会三大业务执行工作台 → 统一财务收口、资产核算与月度经营分析。**

- 业务负责真实单据、执行状态、货物和项目。
- 财务负责发票、银行流水、应收应付、费用分摊、成本结转与月结。
- 一个业务事实只能有一个权威来源，业务与财务通过稳定引用关联；不得复制第二份“交易事实”。

## 四个一级入口

| 一级导航 | 路由 | 主要工作 |
| --- | --- | --- |
| 咖啡业务 | `/coffee` | 散采与辅料、代工生产、到货入库、库存与销售周转 |
| 自行车业务 | `/bike` | 生产采购、国际物流、国内/海外库存与批次成本 |
| 展会项目 | `/exhibition` | 项目预算、合同与费用、样品调度、展会决算 |
| 财务中心 | `/finance` | 收付认领、进销项发票、应收应付、成本/利润及月结 |

全局设置、业务主数据及导入记录通过各工作台内的菜单/快捷入口使用，不再堆叠一级导航。

## 核心规则

1. **全新重构**：重新建表、建 API、建 UI；旧系统只作为业务参考和数据迁移来源。
2. **统一主数据**：业务线、经营主体、往来单位、商品/SKU、仓库、币种独立治理。
3. **业务事实独立**：采购、生产、仓储、销售、物流、展会费用有各自单据；财务只引用，不代替业务主表。
4. **发票与付款分离**：发票不是付款凭证；银行流水不是税务凭证；两者可分别对多张业务单分摊。
5. **库存真实可追溯**：入库、出库、生产领用、退货、调拨都留下不可变流水；销售导入不能重复扣库存。
6. **人工上传优先**：Excel/CSV、银行流水、电子发票是首要入口；1688、吉客云及其他平台 API 可选，不作为系统运行前提。
7. **真实月结**：区分销售发生、退款、库存成本结转、开票与收付款的日期口径，禁止把“已开票/已付款”直接当作收入或利润。
8. **财务可复核**：金额使用 Decimal，多币种记录原币与折算率，确认与关账后不能随意覆盖。
9. **迁移需验收**：旧数据只读提取、来源对账、差异复核、正式切换；绝不直接覆盖旧生产库。
10. **先交付可用闭环**：从采购→入库→销售出库→成本→发票/银行→月报通路验收，避免只有漂亮界面没有账。

## 推荐技术基线

先采用可维护的**模块化单体**，不拆微服务。

- Frontend：TypeScript + React + Next.js + Tailwind CSS
- Backend：Python 3.12 + FastAPI + Pydantic + SQLAlchemy 2 + Alembic
- Database：PostgreSQL；任务/队列按需要采用 Redis + Celery
- Files：对象存储接口（可对接 R2），本地开发使用独立文件目录/兼容存储
- Runtime：Docker Compose；优先支持本地 Mac 开发与受控测试，再发布正式环境

以上是新系统**建议技术设计**，不是已安装或运行成功的声明。
