# Work OS local API

Requires Python 3.11+. SQLite mode uses the standard library only. Optional PostgreSQL/Neon mode uses psycopg. The browser UI and API communicate only over localhost.

```powershell
python backend/run_offline.py  # API: http://127.0.0.1:8106，SQLite 且不读取 .env
```

For explicit PostgreSQL development, `python backend/run_local.py` loads `.env`; use only when a remote database connection is intended. `run_offline.py` forces local SQLite, loopback binding, port 8106 and skips `.env` loading. Keep local SQLite and Neon data separate; no automatic data copy is performed.

Core endpoints: `GET /api/health`, `GET/POST /api/bike/orders`, `POST /api/bike/milestones/due`, `GET/POST /api/bike/landed-costs`, `GET /api/bike/sales`, `GET/POST /api/bike/receipts`, `POST /api/bike/sales/import-row`, `GET/POST /api/projects`, `POST /api/projects/budgets`, `GET /api/projects/samples`, `POST /api/projects/samples/dispatch`, `POST /api/projects/samples/return`, `GET/POST /api/expenses`, `GET/POST /api/platform-income/reconciliation?period=YYYY-MM` (monthly platform/store totals with edit history and amount comparisons), `POST /api/expenses/{id}/allocations` (idempotent project reclassification within the unallocated expense balance), `POST /api/expenses/allocations/{id}/reverse` (audited partial/full reversal using a stable source key; posts an opposite dimension reclassification and returns the amount to the unallocated balance), `GET/POST /api/purchases`, `POST /api/purchases/{id}/receive` (requires stable `source_key` and is idempotent), `POST /api/purchase-receipts/{id}/edit` (revises the original received quantity and synchronizes inventory/payables; refuses reductions below consumed or settled amounts), `GET /api/inventory`, `GET /api/movements`, `GET/POST /api/packaging-rules`, `POST /api/sales/import-row` (idempotent per source row), `POST /api/sales/import` (batch JSON), `GET /api/reports/operating` (optional business-line, legal-entity and project filters), `POST /api/opening-balances` (one-time balanced CNY opening journal; date must precede existing journals and subsequent business entries must be later), `GET/POST /api/bank/accounts`, `POST /api/bank/accounts/coverage`, `POST /api/bank/reconciliation` (period statement check; difference is reported, not auto-adjusted), `POST /api/bank/cash-flow-classification` (audited classification; locked periods cannot be changed), `GET /api/reports/cash-flow?from=YYYY-MM-DD&to=YYYY-MM-DD` (bank-import scope only), `GET /api/accounts`, `GET /api/reports/balance-sheet?as_of=YYYY-MM-DD` (general-ledger classification preview with dated AR/AP and inventory subledger comparisons; not a statutory statement), `GET /api/reports/trial-balance?as_of=YYYY-MM-DD` (posted CNY journals including imported opening balances), `GET /api/journals`, `POST /api/bank/import`, `GET /api/bank/transactions`, `POST /api/bank/fx-review`, `POST /api/open-items/fx-review`, `POST /api/bank/allocate`, `GET /api/receivables-payables`, `GET /api/periods/close-readiness`, and `POST /api/periods/close` (requires a clean readiness check and all review acknowledgements).

Bank import rows and invoices may include `source_system` and `source_document_id` together to identify the originating Admin system and business record. Each pair is unique per record type. A retry with the same external reference and unchanged financial payload returns the existing record; a changed payload is rejected for reconciliation. Existing clients may continue to use `source_key`. These endpoints currently run on the local loopback API and have no authentication or role-based scope; they are not exposed for cross-system production access until service authentication and authorization are implemented.

`POST /api/bank/allocate` and `POST /api/invoices/link` accept an optional `action_key`. Requests are recorded atomically with their result; retrying the same key and payload returns the original result without posting a second settlement or link, while reusing a key with changed data is rejected. If omitted, the API derives a stable key from the canonical operation payload. The same bank transaction and target pair cannot be linked twice with different amounts; revise such a case through a reviewed correction workflow.

Amounts are stored as decimal strings. Coffee receipt and sales posting create balanced journal entries. Coffee inventory uses FIFO layers, and coffee sale imports require a stable source key for idempotency. Posting endpoints compare the payload for a reused source key and reject conflicting retries rather than silently skipping changed data. The coffee workspace supports local purchase entry and CSV sales preview/column mapping. CSV content is read locally by the browser and submitted row by row. This remains a development foundation: supplier refunds/credit notes, return tax documents, invoices/tax confirmation, bank reconciliation, user authentication/authorization, PostgreSQL migrations, and formal period-close review are not implemented. Bicycle receipts are manually reconciled by a stable ALSVID source key and quantity; bicycle sales require reconciled received quantity and post CNY functional-currency journals while retaining original-currency receivables. Foreign-currency settlements can calculate realized CNY FX gain/loss from reviewed rates; period-end revaluation, unrealized FX and bank reconciliation are not implemented. Bicycle landed costs are allocated equally per referenced ALSVID order unit; import VAT is retained as an unposted tax record pending invoice/tax review.

Coffee sales returns use `GET /api/sales/returns` and `POST /api/sales/lines/{id}/return`. New sale postings retain their FIFO stock-layer mapping; returns reverse revenue and COGS, restore the specifically returned finished goods and packaging, reduce open receivables, and record paid-sale refunds as customer payables. Legacy sale lines without complete layer trace are not automatically returnable. Procurement records expose ordered and received quantities and the corresponding original-currency amounts for document reconciliation.



Foreign bank imports require currency and, for non-CNY rows, a reviewed positive CNY exchange rate, rate date, and source. Legacy unvalued foreign bank rows and open items have review endpoints (/api/bank/fx-review, /api/open-items/fx-review). Matching settlements post realized FX gain or loss separately from operating profit. These workflows need business-ledger reconciliation before production use.
